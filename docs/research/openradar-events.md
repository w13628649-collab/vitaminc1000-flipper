# OpenRadar 怎么读事件:背景、原理、实验方法

2026-10-19。研究对象是 [Nouuu/Albion-Online-OpenRadar](https://github.com/Nouuu/Albion-Online-OpenRadar)
(158★,Go + JS,最后推送 2026-10-17)的源码和 `docs/technical/` 下的技术文档。

**目的是学逆向方法,不是做雷达。** 我们的工具只解操作响应、一条事件都不解
(CLAUDE.md 核心要求),这份文档正好说明那条线另一边是什么。

## 一、背景:一条事件长什么样

### 派发字节:Move 有专用快速路径

Photon Protocol18 下,Albion 事件只用两个派发字节:

| 派发字节 | 含义 |
|---|---|
| `3` | **Move**,专用快速路径 |
| `1` | 通用,真实事件码在 `params[252]` |

Move 单独一个字节是因为它压倒性地多。OpenRadar 2026-09-03 的语料(高地、Brecilien、
迷雾两段会话,29,296 个包):

| 事件 | 次数 | 占比 |
|---|---|---|
| 3 Move | 33,937 | **78.6%** |
| 1 Leave | 3,524 | 8.2% |
| 123 NewMob | 1,177 | 2.7% |
| 11 HealthUpdates | 1,142 | 2.6% |
| 39 资源批量刷新 | 544 | 1.3% |
| 29 NewCharacter | 265 | 0.6% |
| 40 资源单个刷新 | 82 | 0.2% |
| 325 地下城入口 | 12 | 0.0% |
| 46 资源被采 | 4 | 0.0% |

一共 125 种事件码,43,192 条。

### 参数是编号字典,不带名字

每条事件解出来是 `map[byte]any`。键是 0、1、2……,**包里不写键的含义**。
"`params[7]` 是坐标"这种知识全部来自逆向。

### 加密消息类型:0x80 | kind

| msgType | 含义 |
|---|---|
| 2 / 3 / 4 | 请求 / 响应 / 事件 |
| 130 / 131 / 132 | 加密的请求 / 响应 / 事件 |

OpenRadar 的文档原话:"`msg_type 132` (53 occurrences) and `130` (3) silently dropped
... Proximity to `msgEncrypted=131` suggests encrypted variants."
**和我们的 parser 一样只认 131、别的静默丢**——`KeySync` 就在这些 132 里。
这是 `client-data.md` 第二点七节那个推测的实证。

## 二、逐个事件拆开

### 资源刷新:39(批量)和 40(单个)

**39 `NewSimpleHarvestableObjectList`** 是"结构数组"布局——一条消息装附近所有资源,
每个字段一个数组,下标对齐:

```
a0[i]                 资源 id
a1[i]                 类型(0–27)
a2[i]                 等阶
a3[2i], a3[2i+1]      X, Y(平铺交错的 float 数组)
a4[i]                 剩余量
```

39 **不带附魔**,先按 0 建,后续由 46 补。

**40 `NewHarvestableObject`** 单个刷新,字段全:

| 键 | 含义 |
|---|---|
| `[5]` | 类型 |
| `[6]` | `mobileTypeId`——区分静态资源和活体(动物) |
| `[7]` | 等阶 |
| `[8]` | `[x, y]` |
| `[10]` | 剩余量 |
| `[11]` | 附魔 |

`mobileTypeId` 是 `null` / `65535` / `-1` 时是静态资源点,是真实 TypeID 时是活物
(能剥皮的动物)。早期靠 `size` 猜,不可靠,后来换成这个。

### 资源被采:46

最简单的一个:

```
[0]  资源 id
[1]  新的剩余量;undefined 表示采空了
```

它们的夹具里能看到一个资源被采的全过程:id 2525 的剩余量 `2 → 1 → 0`。

**不可靠**:有时跳值(3 直接到 1)、第一次采时不发、一次减不止一。
所以处理逻辑只认"undefined = 采空就删",中间值丢了也不影响结果。

### 怪物:123

| 键 | 含义 |
|---|---|
| `[1]` | typeId——**静态表下标 + 16** |
| `[7]` | `[x, y]` 出生位置 |
| `[2]` | 当前血量,**归一化到 0–255**(一个字节) |
| `[13]` | 最大血量,真实值 |
| `[19]` | 稀有度 |
| `[34]` | 附魔 |

当前血量用一个字节传比例而不是真值,是省带宽:真实血量 = `[2] / 255 × [13]`。

怪物**出生**走 123,之后**移动**走 Move(3):`params[1]` 是一个 30 字节的二进制块,
第 9–12 字节是 X、13–16 字节是 Y,小端 float32。

### 玩家出现:29

| 键 | 含义 |
|---|---|
| `[1]` | 名字 |
| `[8]` | 公会 |
| `[51]` | 联盟 |
| `[53]` | 阵营旗:0 和平、1–6 阵营战城市、255 敌对 |
| `[40]` | 装备 id 列表 |
| `[43]` | 技能 id 列表 |

**位置拿不到。** 玩家移动也走 Move,同一个二进制块、同样的 9/13 偏移——但那 8 个字节
和一个 XorCode 做了 XOR,解出来是乱码,常常是 NaN 或无穷大,被 `isFiniteFloat32` 扔掉。
所以 OpenRadar 把玩家对象**一律建在 `(0, 0)`**,画玩家的函数直接 `return`,注释写着
"Disabled: positions are encrypted, all players render at (0,0)"。

XorCode 走事件 `KeySync`(我们码表里 602)下发,而它本身被 Photon 的 AES 包着。

### 地下城:325

`NewRandomDungeonExit`:`[1]` 坐标、`[3]` 名字、`[6]` 模板、`[9]` 附魔、
`[16]` 迷雾入口才有的 `MISTS_*` 标签。

### 迷雾传送门:伪装成怪物

**最反直觉的一条:迷雾传送门不是独立事件,是作为怪物下发的。** 走 `NewMob`(123),
服务端名字形如 `MISTS_SOLO_YELLOW`,靠 `MISTS_` 前缀区分。

- 名字里的颜色是 **PvP 区域标签**,不是稀有度。稀有度在单独的参数里
- 同一种传送门在语料里出现过 5 个不同的 typeId(94、95、96、116、121),
  所以**只能靠名字前缀判,不能靠 typeId**
- 码表里有个名字特别像的 `NewMistsWispSpawn`(526),最初的设计就假设迷雾小精灵走它。
  **实测不是**——它只带 id、坐标和一个 90/180/270 的朝向值

曾经的 bug #145:没加前缀判断时,所有带服务端名字的怪都进了传送门列表,
活动 Boss、能量水晶、周年雕像全被画成了传送门。

## 三、为什么能标资源和怪,标不了玩家

| | 消息格式 | 坐标 |
|---|---|---|
| 资源 | 39 / 40 | 明文 |
| 怪 | 123 出生 + 3 移动 | 明文 |
| 玩家 | 29 出生 + 3 移动 | **XOR 过** |

同一个 Move 消息、同一个字节偏移,**SBI 只对玩家那份加了 XOR**。
PvE 信息(资源、怪)放着不管,PvP 位置护住——而且只花最便宜的 XOR,
密钥每个会话只用一条 AES 消息送一次。

## 四、实验方法——这是最值钱的部分

OpenRadar 的价值不在雷达,在于它把"一个字段一个字段怎么确定含义"的过程都留下了。

### 1. 场景化录制

```bash
tcpdump -i <网卡> -w capture.pcap 'udp port 5056'
```

每次只做一件事(站着不动、采一个矿、进一次区),录一小段。
它的 `PROTOCOL18_PARAM_LAYOUTS.md` 就来自一段 130 秒的录制:T5 区域 + 采集 + 跨区,
3,020 个包、4,954 条事件。

### 2. 全参数倾倒

handler 里大量这种代码:

```javascript
// 🔍 Log ALL parameters for comparison with Event38
for (let key in Parameters) allParams[`param[${key}]`] = Parameters[key];
```

先不管哪个键是什么,**所有键全打出来**,攒够样本再看。

### 3. 差分:做已知动作,看哪个值变

采一下矿 → 看哪条事件出现、哪个值减了一。46 的 `[1]` 是剩余量就是这么定的。

### 4. 锚点样本

找一个**能独立认出来**的样本,反推映射。typeId 偏移就是这么定的:

> wire 116 (server-named MISTS_SOLO_YELLOW, 2026-07-05 capture) → idx 100 = MOB_UNIQUE_MISTS_PORTAL_WISP

这只怪服务端带了名字字符串,在静态表 `mobs.xml` 里一查是第 100 项,
线上 typeId 是 116 → 偏移 16。

### 5. 统计交叉验证

一个锚点不够,要全语料验证。`tools/offset-validate` 把每个 `NewMob` 的
(typeId, 血量, 攻击, 移速)倒成 JSONL,然后检查:**线上血量 `[13]` == 静态表里
`mobs[typeId − 16]` 的血量**,对每一条都成立吗?

结果:**6,469 个 NewMob 事件 + 5,889 条会话日志,零异常。** 之前用偏移 15 时,
靠一个 `t−1` 的补丁凑对了大部分,直到死亡/动态变种上暴露出来。

这个方法的精髓:**线上数据和静态数据是两个独立来源,对上了就是证据,
一条对不上就说明假设错了。**

### 6. 回归夹具

每个场景切一小段 pcap 存进 `internal/photon/testdata/`
(`harvestables/batch-spawn.pcap`、`mobs/spawn.pcap`、`players/spawn.pcap`……),
同时导出成前端能直接喂的 JSON。游戏一打补丁,重跑测试就知道哪里漂了。

### 7. 匿名化 + 审计

`tools/anonymize-pcap` 洗掉 MAC、IP、时间戳和所有已知带名字的参数,
`tools/photon-strings` 再把剩下的字符串按消息类型和参数位列出来,
**还能读出名字就说明字段表漏了一项**。这样夹具才能公开提交。

### 8. 确认 vs 待确认分开写

文档里大量这种话:"Only Common portals were observed post-patch, so the rarity slot
still needs confirmation against a non-Common portal." 见过才写确认,没见过明说。

## 五、版本漂移:真正的维护成本

| 时间 | 改了什么 |
|---|---|
| 2026-06-29 | 上游枚举中间插了两项,**≥248 的事件码全部 +2** |
| Knightfall | 迷雾传送门名字从 `[3]` 挪到 `[15]` |
| Dragonfire 2026-08-31 | `NewMob` 在 `[32]` 插了一个参数,后面全挪一位;地下城在 `[4]` 插了一个 |

Dragonfire 直接把 v2.2.3 搞坏了,README 顶部现在还挂着修复公告。
同一个位置的含义也会变:`NewMob` 的 `[8]` 以前是稀有度,补丁后变成了坐标。

**这就是为什么回归夹具不是可选项。**

## 六、对我们有用的

1. **我们 parser 的加密类型 bug 该补了。** 130/132 被静默丢掉这件事有实证了,
   至少要计数和打日志
2. **场景化 pcap 夹具值得学。** 我们的 op 81/82/197 也会漂(`protocol.go` 注释里
   记过 2026-06-29 那次),现在没有回归夹具,漂了只能靠线上发现
3. **匿名化工具的思路**:我们要是存抓包样本做测试,也得先洗掉名字
4. **边界不变**。OpenRadar 整个活在事件那一侧,正好是我们那条线排除的东西
